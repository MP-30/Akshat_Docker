Q01
Scenario · Production Crash
Your app works on your local machine but crashes immediately after deploying to production. How do you troubleshoot?
▼
Debugging Logs Environment
Scenario Context
Your Node.js app runs perfectly with docker run locally. After CI/CD pushes the same image to production (AWS ECS), containers exit with code 1 within 5 seconds.
Ideal Answer
  • 1
    Check exit logs: docker logs <container_id> and docker inspect for exit code clues.
  • 2
    Compare environment variables — production may be missing a secret or DB URL. Use docker inspect to view env vars.
  • 3
    Verify the image was actually rebuilt. A stale image tag like :latest can silently pull an old build.
  • 4
    Check resource limits — production may have tighter CPU/memory; the app OOMs and exits.
  • 5
    Run the production image locally with production env vars to reproduce: docker run --env-file prod.env myapp
Always use immutable tags (e.g., :v1.2.3 or commit SHA) instead of :latest to prevent silent version mismatches.

Q02
Scenario · Performance
Your Docker image build takes 15 minutes every time. A team member pushes 20 times a day. How do you fix this?
▼
Layer Caching Dockerfile CI/CD
Scenario Context
A Python ML project copies all source files before installing packages, invalidating the pip cache on every single code change — even a comment edit.
Ideal Answer

The root cause is poor layer ordering. Dependencies should be installed before copying source code:

# ❌ BAD — cache busted on every code change COPY . . RUN pip install -r requirements.txt # ✅ GOOD — pip layer cached unless requirements.txt changes COPY requirements.txt . RUN pip install -r requirements.txt COPY . .
  • +
    Use multi-stage builds to keep build tools out of the final image.
  • +
    Use a .dockerignore file to exclude node_modules, __pycache__, .git etc.
  • +
    In CI, use BuildKit cache mounts (--mount=type=cache) to persist pip/npm caches between pipeline runs.

Q03
Scenario · Memory
A production container keeps getting OOM-killed every few hours. How do you diagnose and fix it?
▼
OOM Resource Limits Monitoring
Scenario Context
A Java microservice running in Docker Swarm exits with status 137 (SIGKILL). The on-call team just restarts it, but it happens again every 4–6 hours.
Ideal Answer
  • 1
    Confirm OOM kill: docker inspect --format='{{.State.OOMKilled}}' returns true.
  • 2
    Monitor memory usage: docker stats in real-time, or integrate with Prometheus + cAdvisor for trends.
  • 3
    Check for a memory leak in the app (e.g., Java heap not releasing, connection pool growing unbounded).
  • 4
    Set proper limits and give JVM awareness of the container:
    docker run --memory="512m" --memory-swap="512m" myapp # For Java: add JVM flags ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75"
  • 5
    Configure a health check + restart policy as a stop-gap while the root cause is fixed.
Key insight: Java before JDK 10 was container-unaware — it read the host's total RAM, not the container limit, causing it to over-allocate heap. Always use -XX:+UseContainerSupport.

Q04
Scenario · Networking
Two containers in a Docker Compose file can't talk to each other. How do you debug inter-container networking?
▼
Docker Compose Networking DNS
Scenario Context
A React frontend container tries to call http://backend:5000/api but gets "connection refused." Both services are defined in the same docker-compose.yml.
Ideal Answer
  • 1
    Confirm both are on the same network: docker network inspect <project>_default — both containers should appear.
  • 2
    Use service name as hostname — Docker Compose creates an internal DNS entry per service. ping backend from the frontend container should work.
  • 3
    Check if the backend is actually listening on 0.0.0.0, not just 127.0.0.1 inside its container.
  • 4
    Add a depends_on + healthcheck so the frontend waits for the backend to be truly ready:
services: backend: image: myapi healthcheck: test: ["CMD", "curl", "-f", "http://localhost:5000/health"] frontend: image: myui depends_on: backend: condition: service_healthy
depends_on alone only waits for the container to start, not for the app inside it to be ready. Use condition: service_healthy for real readiness.

Q05
Scenario · Security
A security audit flags your Docker containers as running as root. How do you fix this?
▼
Security Dockerfile Best Practices
Scenario Context
Your company's security team runs a CIS Docker Benchmark scan. It reports that all containers execute processes as UID 0 (root), violating the principle of least privilege.
Ideal Answer

Running as root means a container breakout gives an attacker full host privileges. Fix it in the Dockerfile:

FROM node:18-alpine WORKDIR /app COPY --chown=node:node . . RUN npm ci --only=production # Switch to non-root user before CMD USER node CMD ["node", "server.js"]
  • +
    Use --chown in COPY so the app files are owned by the non-root user.
  • +
    Add --read-only flag and --cap-drop ALL at runtime for defence in depth.
  • +
    Use tools like Trivy or Docker Scout to scan images for vulnerabilities in CI.

Q06
Scenario · Data Persistence
A database container loses all its data every time it restarts. How do you make it persist?
▼
Volumes Database Storage
Scenario Context
Your team runs a PostgreSQL container in staging. Every deployment wipes the DB because it's recreated from the image. QA engineers are frustrated re-seeding data daily.
Ideal Answer

Container filesystems are ephemeral by design. Data written inside a container disappears when it's removed. Use a named volume:

# docker-compose.yml services: db: image: postgres:15-alpine volumes: - pgdata:/var/lib/postgresql/data environment: POSTGRES_PASSWORD: secret volumes: pgdata: # Docker manages this — persists across restarts
  • ↔
    Named volume vs bind mount: Named volumes are portable and Docker-managed. Bind mounts tie you to a host path — fine for dev, risky in production.
  • +
    For production, back up volumes regularly using docker run --rm -v pgdata:/data -v $(pwd):/backup alpine tar czf /backup/pg.tar.gz /data.

Q07
Scenario · Image Size
Your Docker image is 2.3 GB and ECR pull times are slowing deployments. How do you shrink it?
▼
Optimization Multi-stage Alpine
Scenario Context
A Go microservice ships a 2.3 GB image because it was built on golang:latest which includes the full Go toolchain, build tools, and a Debian base — all of which are useless at runtime.
Ideal Answer

Use a multi-stage build to separate build-time from runtime dependencies. Go compiles to a single static binary:

# Stage 1: Build FROM golang:1.22-alpine AS builder WORKDIR /app COPY . . RUN CGO_ENABLED=0 go build -o server . # Stage 2: Minimal runtime (~5 MB!) FROM scratch COPY --from=builder /app/server /server CMD ["/server"]
  • +
    Result: from 2.3 GB → ~10 MB. Pull time drops from 90s to under 3s.
  • +
    Also use .dockerignore to exclude test files, docs, and version-control metadata.
  • +
    Squash multiple RUN commands with && to avoid extra layers.

Q08
Scenario · Secrets Management
A developer hardcoded a database password in a Dockerfile. It's now in the image layers and pushed to Docker Hub. What do you do?
▼
Security Incident Secrets Best Practices
Scenario Context
A RUN command in the Dockerfile used a hardcoded password to seed a DB. The image is public. Even deleting the layer won't help — image history is stored.
Ideal Answer

Immediate steps (incident response):

  • 1
    Rotate the credential immediately. Assume it's compromised the moment it was pushed.
  • 2
    Delete or set the Docker Hub repo to private. Remove the image tag.
  • 3
    Audit access logs for unauthorized DB connections.

Long-term fix — never bake secrets into images:

  • ✓
    Pass secrets at runtime via environment variables or Docker secrets.
  • ✓
    Use BuildKit secret mounts for build-time secrets (never stored in layers):
# Build with BuildKit secret (not stored in image) RUN --mount=type=secret,id=db_pass \ DB_PASS=$(cat /run/secrets/db_pass) ./seed.sh # Build command docker build --secret id=db_pass,src=./secret.txt .
Remember: Deleting a layer in a pushed image does NOT remove it from Docker Hub's storage. Always treat any exposed secret as fully compromised.

Q09
Scenario · CI/CD Pipeline
Your CI pipeline builds a new Docker image on every commit but the registry is filling up fast. How do you manage image lifecycle?
▼
Registry CI/CD Tagging Strategy
Scenario Context
A team of 8 devs merges 15–20 PRs daily. Each merge triggers a build tagged :latest. The ECR registry hits its storage limit within 3 months and old images are never cleaned up.
Ideal Answer
  • 1
    Use a proper tagging strategy — never rely only on :latest:
    # Tag with git commit SHA + branch myapp:main-a3f8c21 myapp:pr-142-b9d1e00 myapp:v2.4.1 # semver for releases
  • 2
    Set ECR lifecycle policies — auto-delete untagged images older than 7 days; keep only the last 10 tagged builds per branch.
  • 3
    Prune in CI: run docker image prune -af after pushing to keep build agents clean.
  • 4
    Don't build on every commit — use path filters to skip image builds when only docs or tests changed.

Q10
Scenario · Zero Downtime
You need to deploy a new version of a containerised service without dropping any user requests. How do you achieve zero-downtime deployment?
▼
Production Health Checks Rolling Update
Scenario Context
Your e-commerce API serves 500 RPS. Every deployment causes a 2–3 second gap where new requests hit a container that hasn't finished starting up yet, returning 502s.
Ideal Answer
  • 1
    Add a HEALTHCHECK to your Dockerfile so the orchestrator only routes traffic to a ready container:
    HEALTHCHECK --interval=10s --timeout=3s --start-period=30s --retries=3 \ CMD curl -f http://localhost:8080/health || exit 1
  • 2
    Graceful shutdown: handle SIGTERM in your app to finish in-flight requests before exiting. Set stop_grace_period: 30s in Compose.
  • 3
    Rolling update strategy in Docker Swarm or Kubernetes: bring up new containers, pass health checks, then drain old ones.
  • 4
    Use a load balancer (nginx, Traefik, ALB) that respects health checks and only routes to healthy upstream containers.
The sequence matters: New container starts → passes health check → load balancer adds it → old container receives SIGTERM → finishes requests → exits. Missing any step creates the 502 window.
